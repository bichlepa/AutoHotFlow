# Migration v1 → v2: deliberate behavior changes

Updated continuously. Silent behavior changes are not allowed: everything that is intentionally different in v2 is recorded here.

| ID | Area | v1 | v2 | Reason | Status |
|---|---|---|---|---|---|
| M-01 | Crash of the engine | A crash of the one process ends everything, running instances are gone | The supervisor restarts the engine, running instances are gone, UIs stay connected and resynchronize | Architecture (processes) | planned |
| M-02 | Dialog elements (`Message_Box`, `Input_Box`, `Select_file`, `Confirmation_Dialog` etc.) | Dialog opens from the execution thread | Dialog opens from a worker process. Window order/focus may differ slightly. | Engine must not block | planned |
| M-03 | Hotkey trigger `Disable` | `hotkey, <key>, off` without window context, a context-bound hotkey can stay active | same `HotIf` context as when it was activated | Bug fix | planned |
| M-04 | Errors in `Element_run` | Error paths called `x_enabled` instead of `x_finish` in 6 elements, the element never ended | Errors are exceptions, the engine sets the result `exception` | Bug fix | planned |
| M-05 | Logs | several threads write under a global lock | `storage` is the only writer. File names and format unchanged. | Architecture | planned |
| M-06 | Variables `global`/`static` | direct file access under lock | Engine keeps a working copy in memory, `storage` writes asynchronously (write-behind). Flushed on exit. | I/O never on the critical path | planned |
| M-07 | Saving a flow | runs under lock in the calling thread, `MsgBox` for demo flows. Writing via `FileDelete` + `FileAppend` (a crash in between loses the file). The backup moves `<name>.txt` instead of `.json` and therefore never creates a backup (`Save.ahk:124-146`). | `storage` writes atomically (temp file + replace) and really creates backups (at most 10). Note for demo flows comes as a UI message, not from the engine. | I/O never on the critical path, data safety | Storage implemented (WI-12: atomic, backups, tests `test_backups_keep_exactly_ten_after_twelve_writes`, `test_hard_kill_during_a_big_write_...`). Demo note (UI) open, phase 3. |
| M-08 | Missing packages when loading | `MsgBox` with a query under lock, file is deleted on "Yes" | Engine sends `cmd.ui.confirmDeleteFlowFile` to the manager | Dialogs only in UI | planned |
| M-09 | Chrome package | present | dropped | Decision of the project owner | decided |
| M-10 | Exit | `criticalSectionCounter`, 4-s emergency brake | two-phase with acknowledgements, deadline 5 s | Architecture | planned |
| M-11 | Execution policy `wait` | ineffective: `executionTask` reads `ExecutionPolicy` at the flow root, the value is under `flowSettings` (`Execution Task.ahk:31` versus `Instances and Threads.ahk:18`). `wait` behaves like `parallel`. | `wait` works as described in the editor: only the first instance of a flow runs, others wait until it ends | obvious v1 bug, the UI offers the option | implemented (WI-21, confirmed by the project owner 2026-10-11, E2; implementation read and confirmed in review on 2026-10-12, E13). New instance state `waiting`, FIFO order per flow by start time (v1 would take the first instance in the order of the instance list, `Execution Task.ahk:19`, `:38`–`:48`), `evt.instance.queued`, see ARCHITECTURE 5.1 and PROTOCOL 4.2, 4.3 |
| M-12 | Policy `stop` | instances are stopped without deadline | deadline 2 s, then hard abort of the worker | Architecture (state machine) | planned |
| M-13 | Connections without target | 154 of 1039 connections in the example flows have an empty or unknown end, silently ignored | ignored and reported with an `f1` log entry on load | Diagnostics | planned |
| M-14 | `LoopStack.Pop` on an empty stack | silently sets `""` | throws `AhfError` (code `internal`), logged, thread ends with `exception` | Do not swallow errors | planned |
| M-15 | Folder name of flows | `<data directory>/Saved Flows/` | `<data directory>/Flows/`. The v1 files are unchanged, they only have to be copied (or linked) into the new folder. Flow files themselves stay the same (JSON, CRLF). | Shorter name, the v1 folder stays untouched on the switch | implemented (WI-12, `src/storage/StoragePaths.ahk`, test `test_v1_flows_round_trip_through_storage_with_same_structure_and_types`) |
| M-16 | Log file: encoding and timestamps | new files with UTF-8 BOM (`FileAppend ... UTF-8`), time local | without BOM (`UTF-8-RAW`, like the flow files). Local timestamps as in v1, conversion from UTC in storage. Line format unchanged. | Uniform encoding, no BOM in text files | implemented (WI-12, `src/storage/LogSink.ahk`, test `test_log_line_has_the_v1_format_and_goes_to_the_log_topic`) |
| M-17 | Element of a waiting thread was deleted (semantics E1, ARCHITECTURE 4.2) | The thread is set to `running`, finds no element function and shows `MsgBox` ("Unexpected error!") inside the critical section (`Execution Task.ahk:71`, `:88`–`:94`). No task is queued, the thread stays `running` forever, the instance never ends (read from the code, not executed) | thread ends with `exception` ("element was removed"), `f1` log, no dialogs from the engine | Bug fix (hang), dialogs only in UI and worker (ARCHITECTURE 2.3, 6.2) | implemented (WI-21), **confirmed** by the project owner on 2026-10-12 (E13) |
| M-18 | Class and name of an element during execution (semantics E1, ARCHITECTURE 4.2) | The stop (`Element_stop_<class>`) takes the class from the current state (`Execution Task.ahk:198`). The `f0` log of a finished element uses the name from the current state (`:161`), empty for a deleted element (assumed) | class and name come from the start of the execution, like the parameters | Consistency: a running element is finished with the state it was started with | implemented (WI-21), **confirmed** by the project owner on 2026-10-12 (E13) |
| M-19 | Loop stack with several connections (WI-21) | If a loop is left via `tail` or `exception` over several connections, the stack is reset per connection (`Execution Task.ahk:119`–`:126`); when entering a loop the stack is always put onto the origin thread, even if a clone runs into the loop (`:142`–`:145`) | The stack is reset once per finished loop element, before cloning. The push on entry only affects the thread that enters the loop (clones are created before the push). | silent bug fix: a second pop throws in v2 (M-14) and lost the second branch, a clone inherited the push of the other branch | implemented (WI-21) |
| M-20 | Worker elements: abort and deadline (WI-27, E3, ARCHITECTURE 6.4) | An element runs in the execution thread of the instance and has no deadline. How a permanently blocked call ends on stop was not checked. | A worker element has no deadline, unless the class sets `JobTimeoutMs`. If the worker does not acknowledge an abort within 2 s, its process is terminated (the cleanup in the element is skipped). A worker with a job is never considered hung and ended, even if it blocks in one call for a long time. | Architecture (processes), decision E3 | implemented |
| M-21 | Output of values for debugging (`d()`), crash report (WI-28) | `d(text, header, wait)` (`v1/Source_Common/Debug/Debug.ahk`) works only with the setting `developing`, shows its own window and waits with `wait=1` (default) in a loop with `Sleep 100` until it is closed. There is no crash report. | `Debug.Dump(value, title)` never blocks and sends the value as an event to the debug window (own process, opened on demand with `--command=debug`), which shows it as readable JSON. There is no setting `developing` and no waiting. In addition the supervisor writes crash reports (`Reports/`, at most 20) on crash, hang, restart limit and repeated errors, and on request from the debug window. | No dialog from the caller's process (CONVENTIONS 3), diagnostics without a debugger, help for porting the elements | implemented (WI-28) |
| M-22 | Default data folder (E33) | `%APPDATA%\AutoHotFlow` (flows in `Saved Flows/`, variables in `Variables/`, `settings.json`) | `%APPDATA%\AutoHotFlow v2` when neither `--data` nor `AHF_DATA_DIR` is given. v2 never writes into the v1 folder; old flows and variables come in through the import (S4) | v1 stays in everyday use until v2 is finished; v2 must not overwrite its variables or settings | implemented (`Supervisor.DataDir`) |
