# Measurements

This document lists the measured values that design decisions rest on. The IDs are `MS-nnnn`; the migration IDs of `doc/MIGRATION.md` are `M-nnnn`, a different series with the same numbers. For each measurement it gives what was measured, how, when, the result, the decision or document it supports, and its status.

Status words:

- **verified**: measured or read, and the number is in the source.
- **assumed**: presumed in the source, not measured.
- **not checked**: not measured.

## Important: one machine, not an idle machine

All numbers were measured on **one machine**, the owner's normal work computer. The machine was **not idle**: VS Code, the v1 AutoHotFlow and other AutoHotkey scripts kept running. No load was removed for the measurements. The values are therefore typical values for a normally used work machine, not benchmark values. They change with the load. Example: an earlier development run measured idle CPU at 0.31 % of the system; the final run measured 0.23 % (MS-0004).

The spikes (MS-0010, MS-0011) ran on a development machine with AutoHotkey 2.0.x. The source gives no further hardware data for them.

Measurement machine (stated in the sources):

- Windows 11 Pro (10.0.26300), 8 logical CPUs, 23.9 GB RAM (stated in WI-0025 only)
- Python 3.13 with `psutil`
- AutoHotkey v2, `AutoHotkey64.exe` (64-bit only, see ARCHITECTURE decision E0004)

## Method

**Test runs.** The stress measurements run with `python -m pytest tests -m stress`. When `AHF_MEASURE_OUT=<file>` is set, each measurement writes one JSON line to that file and prints it as `MEASURE ...`. The Python clients (`tests/stress/stresskit.py`, `StressClient`) wake the hub after each write, as the AutoHotkey roles do. All tests except the long runs ran ten times in a row (`-k "not memory and not backlog"`). Unless stated otherwise, the values are the median and the maximum over these 10 runs (latencies: median of the medians, maximum of the maxima). Memory and handles are read with `psutil`. Idle CPU is the difference of the CPU time (`psutil cpu_times`) divided by the wall-clock time, over 30 s after 5 s of settling.

**Soak and churn.** The soak test (`-m soak`, `tests/stress/test_soak.py`) runs in one process and takes its length from `AHF_SOAK_SECONDS`. Connection churn in the soak run is switched on with `AHF_SOAK_CHURN=1`. Measurements must not run in parallel with other load.

**Spikes.** The spike code (`pipe_server.ahk`, `client.py`) is not in the working tree any more. It is in the git tag `v2-phase2-final` under `work_items/spikes/`.

**Big flows.** `tests/stress/test_big_flows.py` (WI-0024). The cost breakdown (MS-0020) was taken on the largest flow (92,808 characters), the frame and flow sizes in MS-0018 and MS-0019 are as stated in the table.

**Log throughput.** `tests/stress/test_log_backlog.py` and the flood tests (WI-0025). The 1000 lines/s target is measured over 10 s.

**R0003 and load phase (WI-0046).** `tools/measure_r3.py` (VS Code tasks "Tool: R0003 measurement ..."; code state of the numbers: commit `d1ee026`). Run it alone: `python tools/measure_r3.py parse --runs 7` (MS-0027 to MS-0029: synthetic element files in a temporary folder, an entry script that includes `src/AhfBoot.ahk` and the files; rounds alternate over the counts N = 0, 50, 150, 300, in forward and reverse order) and `python tools/measure_r3.py load --runs 3` (MS-0030: the flows and the probe of `tests/stress/test_big_flows.py`, entry with `tools/measure_r3_hooks.ahk`; `--variants plain,stubs`). Memory: `psutil memory_info` (`wset` = working set, `private`), 1.5 s after `ready`. The numbers are medians; `--out FILE` appends the JSON lines. The synthetic elements are about 160 lines each (v1: about 160 lines per element, 162 elements), so N=150 corresponds to the size of v1.

**Memory per role (WI-0047-PREP).** `python tools/measure_r3.py roles --runs 7` (VS Code task "Tool: R0003 measurement, memory per role ..."; `--layout legacy` measures the single entry of before WI-0047-PREP, `--layout entries` or `auto` the role entries). Per run and element count: a session with supervisor, storage, engine (which requests one warm worker), manager (`--ui=stub --headless`) and debug (`--headless`) is started, and 1.5 s after `ready` the private bytes (`psutil memory_info`) of each process are read. The triggerhost is measured on its own as a process with the includes of its entry that idles. The synthetic classes get a mode by index (`synthetic_mode`: every 10th a trigger, then about one third workers). In the `entries` layout the tool copies `src/AutoHotFlow.ahk` and `src/entry/*.ahk` into a temporary folder (relative includes made absolute) and inserts the classes before `AhfMain()` of each entry according to `ROLE_MODES` of `tools/gen_element_includes.py`; the supervisor of that folder starts the roles from its `entry/` folder. The sums are the sums of the medians of the processes, plus 1, 3 or 16 times the median of the worker. Run it alone on the machine (other load changes the values little, but the order of runs alternates over the counts).

**Stub arrival times.** MS-0026 was measured with `GetSystemTimePreciseAsFileTime` from the stub side only.

**Loop passes (WI-0054).** `python tools/ahkrun.py --timeout 500 tests/ahk/helpers/loop_bench.ahk <result file> 100000` (VS Code task "Tool: loop pass benchmark"): one flow per element, the loop's head part connected to its own tail part, run by `Executor.Tick` with `EngineOwner`; the time is from `StartFlow` to the end of the instance (QueryPerformanceCounter). The session measurement is `pytest tests/integration/test_core_c_loops.py -k test_a_long_loop_does_not_block_the_engine --all -n 0 -s` (task "Tool: long loop does not block the engine"), serial, nothing else of the tests running; the `MEASURE long loop:` line has the time per pass and the latencies.

**Element rate (WI-0066).** `python tools/ahkrun.py --timeout 600 tests/ahk/helpers/element_rate_bench.ahk <result file> 20000 5000` (VS Code task "Tool: element rate benchmark"): the same stand-in owner as the loop passes, three measurements (MS-0036); the result file lines are the figures of the row. Run it alone.

**Variable requests of a worker (WI-0050).** `tests/integration/test_worker_vars.py::test_round_trip_of_a_variable_request_from_a_worker` (VS Code task "Tool: variable request round trip from a worker"): the test element `Action_TestVarBenchWorker` (`tests/elements/`) calls `ctx.GetVar` 300 times in a worker and measures every call with `QueryPerformanceCounter` inside the worker; the path is worker, hub, engine, hub, worker, in a session of the flow runner (supervisor, storage, engine, warm worker). Serial, nothing else of the tests running.

**Unassigned keys for input tests (WI-0064 spike, E0059).** A script registers `vk97` (plain), `$vk98` (keyboard hook), `~vk99` (hook, key passes on) and `vk9F` (plain). A second process sends each key with `SendInput` (key down and up, `wVk` only, scan code 0), 0.4 s apart, while the listener runs (`tools/ahkrun.py`, AutoHotkey 2.0.30, interactive session, no window of the test). Result of 4 runs: in runs 2 to 4 every key fired once; a second listener variant (`$vk98`, `$*vk9A`, `$vk9B`, `vk9C`, with an `InputHook` for the keys) fired every key too. The plain keys fired in every run. In run 1 the two hook keys (`$vk98`, `~vk99`) did not fire, the plain ones did. The cause is not known (not reproduced in the three later runs). Verified: these 4 runs of the spike (not the test suite). Consequence: the input tests must not treat one miss as proof either way.

## Not measured

These points are missing from the measurements. The first group is listed in the source as "not measured" or "not checked".

- Memory with 5 open editors (MS-0006). There is no editor role.
- Engine state change until editor redraw (MS-0007). There is no editor.
- Latency with an AutoHotkey client as the other end. Only the Python client was used.
- Triggerhost (WI-0014) was not built and is not part of the runs.
- Worker elements (pool) were not put under load.
- The 10-minute soak with connection changes (`AHF_SOAK_CHURN=1`) was not run. At the time of WI-0016 it would have failed on F-0006; the source does not say that it was run after the fix.
- The 600 s soak with the new rate (WI-0025) was not run.
- The cause of the 0.56 s start with one flow (MS-0009). The source does not rule out an influence of the test run before it.
- The storage maximum log throughput (MS-0022). The value shown is limited by the sender.
- Memory with a full log queue (the WI-0025 limit was reached in a test, but its memory was not measured).
- Log time budget values of 5, 20 and 50 ms. Only 10 ms was used, and no other value was compared.
- Ping latency during a log flood. Only `flow.read` was measured (under 200 ms).
- The cost of up to 500 `evt.log.entry` sends in one bundle. They run in the same timer run and may exceed the 10 ms budget.
- Several hundred log sources. Only 4 sources were tested.
- Effect of `FlushFileBuffers` on a power failure. Not testable in this setup.
- Whether `OpenProcess` returns "access denied" (error 5) in practice.
- Idle CPU as "sum of the processes in percent of one core". Decision E0005 applies the target to the whole system, so this reading is not a target any more.
